The existing state machine was expanded rather than replaced: the new `poster.SessionState` records the 15 required states `CHROME_NOT_FOUND`, `CHROME_STARTING`, `CDP_CONNECTING`, `CDP_CONNECTED`, `SESSION_CHECKING`, `SIGNED_IN`, `LOGIN_REQUIRED`, `ROBOT_CHECK`, `WAITING_FOR_USER`, `RECOVERING`, `RESUMING_TASK`, `DRAFT_SAVED`, `AWAITING_APPROVAL`, `BLOCKED`, and `FAILED_RETRYABLE` with the timestamp, task id, browser PID, CDP port, profile path, current URL, state, decision, and reason, and `poster.redact_secrets` removes any password, cookie, session token, authorization header, or API key before it reaches a log or a state file. Four root causes were found in the code. `_known_debug_ports` returned ports from the port file and the process command lines without checking that the endpoint still answered, so a stale port was handed to Playwright and silently skipped. `launch_detached_chrome` had one failure path, so "Chrome closed", "CDP disconnected", "invalid endpoint", and "locked profile" all ended in the same blind relaunch that could open a second window on the same profile. `SmartAgent.pause_for_user` never checked whether the CDP connection had survived while the user was solving the challenge, so the flow continued on a dead page. `post_to_tiktok_studio` always re-uploaded because no persisted state was consulted, so an interrupted run could create a duplicate draft. The fixes are `poster.cdp_endpoint_alive`, `poster.chrome_pid_for_port`, `poster.chrome_processes_for_profile`, and `poster.profile_is_locked`, which separate those cases so a live Chrome for `data/chrome-profile` is reattached over CDP on its existing page, a stale port is discarded as `RECOVERING`, a locked profile raises a clear error instead of a second window, and a genuinely absent Chrome is restarted with the exact same profile, the real `chrome` channel, and `headless=False`. `SmartAgent.pause_for_user` now probes the page after the user presses Enter and, when the connection dropped while the Chrome window stayed open, reattaches to the same running Chrome through a `reconnect` callback and continues on `RESUMING_TASK` without a new tab or a second sign-in; an unsolved challenge still ends as `BLOCKED` with the video kept. `post_to_tiktok_studio` gained a resume path: a task that already reached `DRAFT_SAVED` is not uploaded again and creates no duplicate draft, a task that reached `UPLOADED` continues at the caption step, and the new `UPLOADING` and `UPLOADED` statuses are persisted so an interrupted upload is visible on the next run. `workflow.load_resume_state` and `workflow.record_workflow_state` read and persist the stage atomically, `main.py --resume` resumes an interrupted task id, and `storage.load_task_state` and `storage.save_task_state` provide the durable task state.
